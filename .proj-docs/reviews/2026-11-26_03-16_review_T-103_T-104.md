## 🟡 Warnings

- **W-038**　`packages/catalog/src/album-info/parseAlbumInfo.ts:104-105`、`:40-44`；測試 `parseAlbumInfo.test.ts:222-237`
  - **L1**：Functional Spec D68 規定「最多 16 KB、1,000 行；超過 = 檢查結果」。`isTooLarge()` 嘅註解亦講明想先用便宜嘅 `text.length` 擋。
  - **L2**：`songLines(text)` 喺 `isTooLarge()` 之前已經拆晒成段文字。20 MB 全部係換行嘅輸入要 1 648 ms 先回 `INFO_TOO_LARGE`；20 MB 冇換行要 35 ms。另外有 3 個 mutant 冇被捉到：M01 刪走 `byteLength` 一句、M02 byte 上限 `>` 改 `>=`、M03 `length` 捷徑 `>` 改 `>=`。原因係唯一嘅測試用 `16 KiB + 一行` 嘅 ASCII，長度本身已經過咗上限，試唔到 byte 規則同邊界。
  - **L3**：Worker（T-105 / T-106）會先睇檔案大細，所以 production 實際風險低。但 package 係純函數，會直接收外來文字。
  - **方案 A（推薦）**：先 `text.length > INFO_TEXT_MAX_BYTES` 即回，之後先 `songLines()`，再查 byte 同行數。加 3 個測試：16 384 byte 收；16 385 byte 唔收；約 6 000 個中文字（長度少過 16 384、byte 多過上限）唔收。
  - **方案 B**：喺 parser 入面數 `\n`、`\r` 嘅數目，夠上限就停，唔拆行。改動較大，好處只係唔使分兩步。
- **W-039**　`apps/api/test/albumsList.test.ts:89-96`（被測：`apps/api/src/albums/overview.ts:62`）
  - **L1**：Functional Spec D69、Technical Spec API-010 規定列表次序 = `albumOrder()`。
  - **L2**：mutant M38 拎走 `.sort(byAlbumOrder)`，所有測試照過。原因係測試嘅 id（`l m x y z`、`a b`）啱啱好已經係預期次序；D1 嘅 `GROUP BY a.id` 本身就按 id 出，所以排唔排都一樣。
  - **方案 A（推薦）**：id 嘅字母次序同預期次序要相反，例如 `single-01-a`、`ep-01-b`、`album-10-c`、`album-02-d`，預期 `d c b a`。
  - **方案 B**：直接測 `byAlbumOrder`。不過 route 有冇用佢仍然冇測到，所以唔夠。
