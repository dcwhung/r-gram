## 🟡 Warning

**W-020** `apps/api/src/catalog/rebuild.ts:74-81`：「冇變」嘅一輪唔寫 R2，所以 R2 etag 唔變。另一個讀 D1 比較早、未寫完嘅生成，之後條件寫入會成功，用舊資料蓋過去。
- **L1**：違反 rebuild.ts 頭兩條保證（「舊嘅 document 永遠蓋唔到新嘅」、「成功返回時生效嗰份已經包括佢嘅修改」），同 Technical Spec 核心原則 1、FR-121（儲存即生效）。
- **L2**：scratch copy 用 workerd probe 重現到。初始 D1 同 live 都係 `T1`。請求 B 將 D1 改做 `T0`，佢嘅生成 head 到 E1、讀 D1 得 `T0`，準備寫入。請求 A 喺呢個時候將 D1 改返 `T1`，佢嘅生成 head 到 E1、讀 D1 得 `T1`、hash 同 E1 一樣，所以回 `ok: true, unchanged: true`，乜都冇寫。之後 B 寫入，條件係 `etagMatches E1`，因為 etag 冇變所以成功。結果 D1 係 `T1`，live `catalog.json` 係 `T0`，`catalog_state.status = 'ok'`。管理端冇提示，直到下一次改到內容先會更正。
- **L3**：要兩個寫入請求重疊，而且後面嗰個將值改返 live 嘅值，例如兩個分頁，或者快速改完即刻改返轉頭。發生機會低，但發生咗就係冇人知嘅不一致。
- **方案 A（推薦）**：寫入成功之後再讀一次 D1 snapshot。如果 content hash 同啱啱寫入嗰份唔一樣，就喺 `CATALOG_WRITE_ATTEMPTS` 之內再做一輪。保留決定 1 同 spec 嘅「hash 冇變就唔寫」。代價係每次改到內容多一個 D1 batch。
- **方案 B**：「冇變」嗰輪都用條件寫入，以 `etagMatches current.etag` 寫一份 `generatedAt` 新嘅（bytes 唔同，etag 就會變），咁未寫完嘅舊生成會撞到 conflict。公開 ETag 係 content hash，唔會變，播放端照收 304。代價係每次儲存多一個 R2 寫入，而且要改 spec「冇變就唔寫」。
- 要加一個測試，就係上面嘅 probe（`bucketWith` 嘅 put hook 入面行 A）。

**W-021** `apps/api/src/albums/routes.ts:79`（B-048；`tracks/routes.ts:43,84` 已經係咁）：route 喺 `afterWrite` 生成之前已經由 R2 刪走歌詞檔，而且唔理生成結果。
- **L1**：違反 D30 / 核心原則 1「生成失敗……播放端繼續用上一份內容」，因為上一份內容而家指住已經刪咗嘅檔。
- **L2**：probe 重現到。先生成一份 catalog（歌 `a-01` 有歌詞），再加一張 `wheel_key = 'ABC'` 嘅碟（例如 seed 資料或者規則改過），之後 `DELETE /api/albums/a?force=1`。結果係 200、`catalog: { ok: false, INVALID_DOCUMENT }`；live catalog 仲列住 `lyrics: "a-01.json"`，但 R2 嘅檔已經冇咗，播放端打開呢首歌會 404，直到 catalog 再生成成功。生成成功嘅情況下都有一段時間：播放端 cache 住嘅舊 catalog（`max-age=60` 加本機 fallback）會指住已刪嘅舊歌詞檔。
- 讀 code 見到另一個問題：`dropUnusedLyrics` 嘅 R2 `delete` throw 會令已經刪咗 D1 嘅請求回 500，而且唔會生成，catalog 仲列住嗰張碟。
- **方案 A（推薦）**：route 將要刪嘅檔名放入 context（`c.set('lyricsToDrop', …)`），`afterWrite` 喺 `rebuildCatalog()` 回 `ok: true` 之後先行 `dropUnusedLyrics`，失敗就 log，唔影響回應。並發儲存同一份歌詞嗰個缺口同而家一樣，已經寫明咗。
- **方案 B**：唔即刻刪，之後掃描，只刪 D1 同 live catalog 都冇用、而且 R2 `uploaded` 早過一段時間嘅檔。呢個做法可以避開 developer 擔心嘅並發問題，但多一個排程。
