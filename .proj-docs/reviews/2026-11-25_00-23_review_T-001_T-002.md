## Warning

### W-001 `parseLrc`：行頭 tag 唔係純數字就成行當 metadata，歌詞行靜靜哋消失

- **位置**：`packages/catalog/src/lrc/parseLrc.ts:66`（`break`）、`:83-87`（`LEADING_TAG.test(source) → metadata`）
- **L1**：Functional Spec US-106 驗收（第 626 行）「時間戳格式正確；錯誤逐行指出（行號 + 原因）」；第 625 行只講「其他 metadata tag（`[ti:]`、`[ar:]` 等）忽略」。
- **L2**：`parseLrc('[00:01.00]a\n[00:1O.00]第二句\n[00:03.00]c')` → `lines` 得 2 行、`errors: []`（第 2 行係字母 O）。同樣靜靜哋掉行：`[00:02,50]b`、`[00:02.50 ]b`、`[00：02.50]b`（全形冒號）、`[Chorus]副歌歌詞`、`[]x`、`[aa:bb]a`。
- **L3**：`readTimestamps` 遇到唔係 `[\d:.]+` 嘅 tag 就停，`times` 係空，之後只要行頭有 `[…]` 就當 metadata。管理端「逐行驗證」唔會標呢行，儲存後播放端少咗一句歌詞，冇人知。
- **關於 red → green 改 test**：`[by:me]` 自己一行係合法 metadata，呢個判斷啱。但原本個 case 係 `[aa:bb]a`（tag 後面有歌詞）；green commit 將佢由 it.each 拎走，換成 `[by:me]` 獨立一行，即係「非數字 tag + 歌詞」呢類輸入而家冇任何 test，而實作亦去咗最寬鬆嗰邊。修正只啱一半。
- **方案 A（推薦）**：metadata 收窄做「成行只有一個 `[key:value]`，key 由字母或 `#` 開頭」；其他以 `[` 開頭嘅行報 `INVALID_TIMESTAMP`。`[by:me]`、`[ti:歌名]`、`[length:03:20]` 照樣忽略；`[aa:bb]a` 回到 red commit 原本嘅期望。Trade-off：`[Chorus]` 呢類段落標記會報錯（符合第 627 行「冇時間戳嘅純文字唔可以儲存」）。已喺 scratch copy 驗證：現有 21 個 LRC test 全過，`[aa:bb]a`、`[00:1O.00]b`、`[00:02,50]b`、`[Chorus]c`、`[]x` 都報 `INVALID_TIMESTAMP`。
- **方案 B**：保持寬鬆，另加 `warnings`（`IGNORED_TAG` + 行號）俾管理端顯示。Trade-off：改咗 spec 寫明嘅 `{ lines, errors }` 形狀，而且唔會擋住儲存。
